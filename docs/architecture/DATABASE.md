# Database conventions and migration policy

Normative for every persistence change. Established by M00-006; see also
[ADR-014](adr/ADR-014-durable-identifiers-and-naming-policy.md).

## Durable identifiers

1. Internal identity is a **UUIDv7** (`Guid.CreateVersion7()`), generated by the
   application layer when an aggregate is created — never by the database and never by a
   provider. UUIDv7 is time-ordered, which keeps B-tree indexes healthy under insert-heavy
   workloads (the reason UUIDv4 is forbidden for primary keys).
2. PostgreSQL stores them in native `uuid` columns.
3. Provider IDs, emails, phone numbers and other mutable/natural keys are mapping
   attributes only; they never become primary or foreign keys.
4. Public/external references that must not be enumerable use separate opaque tokens,
   decided per feature; internal GUIDs are never exposed as API surface by default.

## Naming conventions

Enforced automatically by `GetCode.Persistence.Conventions.NamingConventions`, applied to
every model after entity configurations run. Explicit configuration always wins.

| Object | Pattern | Example |
|---|---|---|
| Table | snake_case plural of the CLR name | `outbox_messages` |
| Column | snake_case | `occurred_at_utc` |
| Primary key | `pk_{table}` | `pk_outbox_messages` |
| Unique constraint / alternate key | `ux_{table}` | `ux_wallets` |
| Foreign key | `fk_{table}_{principal_table}` | `fk_orders_quotes` |
| Index | `ix_{table}__{columns}` | `ix_outbox_messages__processed_at_utc_occurred_at_utc` |

Schema-shape is executable-reviewed by `SchemaShapeTests` against real PostgreSQL.

## Migration rules

1. Schema changes happen **only** through EF Core migrations committed next to the change
   that needs them. No manual SQL patches, no `EnsureCreated`.
2. One migration per logical schema change, named `<YYMMDDHHMMSS>_<Intent>` via
   `dotnet ef migrations add <Intent>`. Generated files are not hand-edited.
3. Every migration is reviewed as SQL before merge:
   `dotnet ef migrations script --idempotent -o review.sql` (baseline artifact:
   `docs/operations/sql/0001_baseline.sql`).
4. `Down()` must exist even where it is operationally unused; it keeps rollback reasoning
   explicit in review.

### Expand/contract

Online-safe changes follow expand → migrate code → contract:

- **Expand**: add new nullable column/table/index in migration N; deploy code that writes
  both shapes or tolerates absence.
- **Migrate data**: backfill in idempotent batches inside later migrations or a worker job;
  never in the same transaction as DDL for large tables.
- **Contract**: only after telemetry confirms no reader depends on the old shape, drop
  legacy objects in migration N+k. Never rename-and-drop in one release.

Destructive operations (drop table/column, narrow a type) additionally require the
release-gate checklist in `docs/roadmap/MILESTONES.md` and a restore-tested backup
(see `docs/operations/BACKUP_RESTORE.md`).

### Production execution rules

- Applications do **not** auto-migrate at startup. Migrations run through an explicit step
  (migration bundle executed by the deployment pipeline, or a dedicated one-shot job)
  before the new application version receives traffic.
- The migration step takes a PostgreSQL advisory lock so concurrent deploy jobs cannot
  race (`SELECT pg_advisory_lock(...)` around bundle execution).
- Backup immediately before executing migrations on production; verify it exists before
  proceeding.
- Long-running backfills are executed as resumable batch jobs, not inside a migration's
  single transaction.

## Money and timestamps

- Monetary amounts: `numeric(precision, scale)` with explicit currency codes; never float.
- UTC timestamps: `timestamp with time zone` (`DateTimeOffset` in C#); property names end
  with `Utc`.
